## 5. Находки с доказательствами и ссылками на источник

### FND-001 · High (Высокий) · Детали интеграции (Подтверждённый дефект)

- **Требования:** REQ-007
- **Расположение в источнике:** Раздел «Часть B. REST API -> Общие параметры», строки 104, 108–109
- **Цитата / свидетельство:** «REST type | GET
Request URL | Dev: `/alerts/saveLimit` . Prod: —
CURL | `curl -G "$BASE/alerts/saveLimit" -H "Authorization: Bearer $TOKEN" --data 'cardId=demo-42&amount=50000&enabled=1'`»
- **Объяснение:** Операция сохранения/изменения настроек реализована через HTTP GET с передачей параметров в query-строке. Использование GET для модификации данных нарушает стандарты RESTful API и приводит к передаче конфиденциальных параметров и идентификаторов в URL (риски логирования в прокси, кеширования и т.д.). Для изменения состояния должен использоваться метод POST или PUT с телом запроса JSON.
- **Рекомендация:** Изменить REST type на POST или PUT, перенести параметры запроса из query-строки в JSON request body.

### FND-002 · Medium (Средний) · Противоречие (Подтверждённый дефект)

- **Требования:** REQ-007
- **Расположение в источнике:** Раздел «Часть B. REST API -> Параметры запроса -> Request body», строки 147–148
- **Цитата / свидетельство:** «Content-Type: application/json .
Тело не используется.»
- **Объяснение:** Задано требование заголовка «Content-Type: application/json» при одновременном указании «Тело не используется», что создает противоречие для клиентов API и разработчиков.
- **Рекомендация:** Удалить заголовок Content-Type: application/json при использовании GET-запроса с query-параметрами либо перевести метод на JSON body согласно заголовку.

### FND-003 · High (Высокий) · Противоречие (Подтверждённый дефект)

- **Требования:** REQ-007
- **Расположение в источнике:** Разделы «Часть B. REST API -> Статусы -> 200. Successful — Created», строки 165, 171
- **Цитата / свидетельство:** «#### 200. Successful — Created
```json
{"result":"ERROR","message":"Проверьте сумму"}
```»
- **Объяснение:** Ошибки бизнес-валидации (например, неверная сумма) возвращаются с HTTP статусом 200 OK и телом `{"result":"ERROR", ...}`, что нарушает стандарты REST API. Ошибки клиентской логики и валидации должны возвращаться с кодами HTTP 400 или 422.
- **Рекомендация:** Исправить код возврата для бизнес-ошибок валидации на HTTP 400 Bad Request или HTTP 422 Unprocessable Entity.

## 8. Итоговое заключение и приоритезированные рекомендации

**Вердикт:** Требуется доработка
- **Можно ли начинать разработку:** Нет
- **Можно ли начинать тестирование:** Нет

Документация содержит критические дефекты интеграционной спецификации: использование метода GET для модификации данных (сохранение настроек), возврату ошибок бизнес-логики со статусом HTTP 200, а также полное отсутствие метода для чтения настроек, заявленного в функциональных требованиях. Наличие этих дефектов делает невозможным безопасную реализацию и тестирование функционала.

### Приоритезированные рекомендации

1. Заменить метод HTTP GET на POST или PUT для эндпоинта сохранения настроек и перенести параметры из query-строки в тело запроса в формате JSON.
2. Исправить обработку ошибок бизнес-логики, переведя их с HTTP 200 OK на стандартные коды HTTP 400 или 422.
3. Разработать и добавить в дочернюю спецификацию (Часть B) метод API для чтения текущих настроек уведомлений, чтобы выполнить требования Части А.
4. Устранить расхождения в типах данных между запросом (integer) и ответом (string) для полей amount и enabled.
5. Заполнить пропущенные параметры среды Production и актуализировать ссылки на Swagger-документацию.
